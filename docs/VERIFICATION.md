# 검증 결과

2026-09-06 · `codex/ui-experience-refresh`

현재 제품은 개인 API 키 입력을 제공하지 않는다. 아래 초기 키 연결 시나리오는 당시의 기록이며, 마지막 “서비스 제공 방식 전환” 검증으로 대체한다.

## 통과

- `npm run build`: Next.js 프로덕션 빌드 및 strict TypeScript 검사.
- `npm test`: 10개 도메인·API 테스트.
- 신규 토너먼트·탐색·설정·공통 컴포넌트·테스트 파일의 ESLint 검사.
- 프로덕션 서버(`next start`, 포트 3001)에서 Playwright 전체 사용자 흐름.
- 실 OpenRouter 공개 카탈로그 조회. 배치 모델, 텍스트 출력이 없는 모델, 유효하지 않은 가격은 필터링.

## 브라우저 시나리오

1. 주제 검색 → 북마크 → 새로고침 후 저장 유지 → 주제 자동 입력.
2. 참가 모델 4개 선택 → 중복/초과 선택 방지 → 심판 선택 → 키 없이 대진표 생성.
3. 테스트 키 입력 → 1차전 완료 → 승자 진출.
4. 2차전 오류 → 발언 보관, 결승 슬롯 미정 유지.
5. 재시작 → 중단 → 다시 시작 → 이전 응답 무시 → 새 판정 적용.
6. 결승 → 챔피언 → Markdown 내보내기 → 새로고침 후 유지.
7. 기록 검색의 빈 결과와 복원.
8. 8강 7경기 생성 → running 상태에서 재접속 시 interrupted 복원.
9. 320·390·768·1024·1440px 대진표의 페이지 가로 넘침 없음.
10. 설정·가이드·알림·피드백·약관·기존 주제 설정·참가자 선택의 모바일 렌더링.

모델 API와 경기 응답은 격리된 테스트 컨텍스트에서 fixture로 대체했다. 프로덕션 브라우저 검증에서 pageerror는 발생하지 않았다. 스크린샷·테스트 내보내기는 `/tmp/letsdebate-qa`에 생성한다.

## 남아 있는 실제 연결 검증

사용자 OpenRouter 키가 아직 제공되지 않아 유료 모델별 실제 토론·심판 호출은 미검증이다. 실키를 받은 뒤 저비용 모델의 퀵 매치 한 경기로 스트리밍·판정·OpenRouter 청구 모델 ID를 확인해야 한다. 물리 iPhone의 네이티브 제스처나 배포 환경의 SSE 시간 제한도 이번 로컬 브라우저 검증에는 포함하지 않는다.

기존 전체 저장소의 ESLint 경고를 정리하는 작업은 범위에 포함하지 않았다. Git push, PR 생성, 배포는 수행하지 않았다.

## 스포츠 컵 디자인 후속 검증

- Jua 제목 폰트가 실제 computed font-family에 적용되는지 확인했다. 기존 5종 캐릭터·MC·로고의 이미지 로딩 오류 없음.
- 메인 320·390·768·1024·1440px 가로 넘침 없음. 모바일은 1열, 넓은 데스크톱은 소개·경기장 2열.
- 프로덕션 빌드, TypeScript, 수정 파일 ESLint, `git diff --check`, 도메인/API 10개 테스트 통과.
- 업데이트한 프로덕션 서버 3001에서 기존 4강·8강·심판 선택·중단·실패·결승·내보내기·기록 복원 시나리오 통과. pageerror 없음.
- 브라우저 fixture에 서로 다른 제공사 ID를 사용해 캐릭터가 모델 선택부터 우승까지 이어지는 화면도 확인했다. fixture 모델은 실제로 호출하지 않는다.
- 개발 서버 3000에서는 설정·기존 참가자 화면 최초 접근 중 간헐적인 React hydration 경고가 관찰됐다. 해당 HTML 원문과 JavaScript 비활성 DOM의 main 구조는 정상이었고 후속 접근에서는 재현되지 않았으나, 근본 원인은 확정하지 못했다. 이를 해결했다고 간주하지 않는다. 미리보기는 전체 시나리오를 통과한 프로덕션 서버 3001을 사용한다.

## 히어로 여백·주제 캐릭터 후속 검증

- 프로덕션 빌드와 strict TypeScript, 수정한 `TopicCard.tsx` ESLint, `git diff --check` 통과.
- 320·390·768·1024·1112·1440px에서 페이지 가로 넘침 없음. 1024px 이상은 소개·경기장 2열이며, 모든 확인 폭에서 경기장 오른쪽 끝이 히어로 컨테이너 끝과 일치한다.
- 1112px에서 큰 원형 얼굴 6개와 CTA 3개를 확인했다. 히어로·팀 소개의 선수 카드와 추천 주제의 얼굴 중심 표현이 구분된다.
- 첫 추천 주제의 “이 주제로 토론하기”를 클릭해 `/tournament/new?topic=85` 이동 및 선택한 주제 자동 입력을 확인했다. 경기 실행은 하지 않았다.
- 기존 미리보기를 업데이트한 프로덕션 서버 3001로 새로고침하고, 반응형 검증용 화면 크기 설정을 원래대로 복원했다.

## 서비스 제공 방식 전환

- 프로덕션 빌드·strict TypeScript·핵심 서비스/토너먼트/공통 UI 파일 ESLint 통과. 도메인/API 15개 테스트 통과.
- 서버 키로만 연결, 개인 키 필드 거부, 미설정 503, 운영자 제공 모델 제한, 기존 토론 API의 개인 키 우회 거부를 모의 provider로 검증했다.
- 프로덕션 서버 3001에서 기존 키 저장소 삭제·다른 저장소 보존·키 없는 경기 요청·준비 중 오류 후 재시작·4강 결승·8강 대진표·중단·실패·내보내기·복원을 확인했다. 브라우저 pageerror 없음.
- 메인 320·390·768·1024·1112·1440px 가로 넘침 없음. `/settings`의 `/help` 이동과 보조 화면의 키 입력 제거를 확인했다. 결과 이미지는 `/tmp/letsdebate-managed-ai-qa`에 저장했다.
- 기존 엔진 파일을 포함한 넓은 ESLint 검사에는 `any`, hook 이름·ref 읽기 등 기존 오류가 남아 있다. 해당 패턴이 기존 HEAD에도 있음을 확인했으며 이번 키 관리 전환에서 전체 엔진 리팩터링은 하지 않았다.
- 실제 운영용 키는 아직 제공받지 않았다. 유료 모델 실호출은 수행하지 않았으며 테스트용 요청은 격리된 모의 응답을 사용했다.

- 메인·주제·기록·토너먼트·도움말·의견 보내기와 기존 토론 화면의 제목·버튼·상태 안내를 교정했다. 제목의 불필요한 쉼표·마침표를 제거하고 띄어쓰기와 용어를 정리했다.
- 프로덕션 빌드와 strict TypeScript, 변경한 핵심 화면·공통 컴포넌트·토너먼트 훅/저장소 ESLint 통과. 기존 단위/API 테스트 15개 통과.
- 모의 응답으로 주제 선택·모델 선택·4강/8강·오류 및 중단 복구·우승·기록 내보내기 전체 브라우저 흐름 통과. 실제 유료 AI 호출은 하지 않았다.
- 메인 320·390·768·1024·1112·1440px 가로 넘침 없음. 모바일·데스크톱 기록 화면의 제목과 안내 문구를 직접 확인하고 미리보기 크기를 복원했다. 스크린샷은 `/tmp/letsdebate-korean-copy-qa`에 저장했다.

## AI 토론 배틀 메시지 후속 검증

- 메인 제목·모델 이름 목록·구체적인 예시 주제·토론 흐름을 확인했다. 팀 소개는 모델 이름을 주 제목으로 표시하고 캐릭터 이름은 보조로 표시한다.
- 프로덕션 빌드·strict TypeScript와 수정한 화면/컴포넌트 ESLint 통과.
- 기존 브라우저 시나리오를 변경된 제목에 맞춰 실행했다. 주제 검색·저장·자동 입력, 4강/8강 선택, 경기·중단·오류 복구, 우승과 기록 내보내기 통과. 실제 유료 AI 호출 없이 모의 응답을 사용했다.
- 320·390·768·1024·1112·1440px에서 메인 가로 넘침 없음. 실제 미리보기의 데스크톱·390px 모바일 첫 화면에서 제목·모델 목록·예시 대결을 직접 확인했다. 임시 viewport를 복원했다.
- 검증 이미지는 `/tmp/letsdebate-ai-battle-qa`에 저장했다.

## 캐릭터 20종과 PR 준비

- 캐릭터 이미지 20개는 서로 다른 1254×1254 PNG다. `/characters`에서 20개 이미지 로딩과 원본 다운로드, 메인에서의 이동을 확인했다.
- 카드 모음은 320·390·768·1024·1112·1440px에서 가로 넘침이 없고 브라우저 실행 오류가 없었다.
- PR 범위는 현재 UI·1대1 토너먼트·서버 OpenRouter 연결·캐릭터 컬렉션이다. 로그인과 서버 사용량 제한은 사용자 요청에 따라 이 PR의 Codex 리뷰를 마친 뒤 별도로 구현한다.
- 현재 경기 API에는 로그인·서버 사용량 차감·비용 원장이 없다. 운영 키를 연결한 공개 실행은 후속 운영 제한을 갖춘 뒤 진행한다. 기존 사용량 API도 새 토너먼트 실행의 제한으로 간주하지 않는다.
